1. **Architecture decisions and rationale.** Record that we intentionally chose a two-pass STT architecture: `gpt-live-transcribe` for perceived latency, original audio retained locally, `gpt-transcribe` as the authoritative second pass, then `gpt-5.6-luna` for conservative cleanup. Also record why we rejected using only live transcription, why cleanup must operate after re-transcription from audio, and why provisional text initially lives in an overlay instead of being inserted directly into arbitrary apps.
    
2. **Product principles.** The important ones are: BYOK/direct-to-provider rather than trusting a dictation SaaS; local-first handling of audio; live text should feel immediate but may be wrong; final text should prioritize correctness; cleanup must preserve meaning rather than "improve" the user's ideas; failure of a later stage must never lose the user's dictation.
    
3. **Source-of-truth hierarchy.** This is easy to forget but architecturally important:  
    `original audio > GPT-Transcribe canonical transcript > cleaned transcript > Live-Transcribe provisional transcript`.  
    The cleaned version is what normally gets inserted, but the canonical transcript must remain recoverable through a P0 Copy original transcript action until the session is explicitly discarded.
    
4. **Latency philosophy.** We're optimizing **perceived latency** and **release-to-insertion latency** separately. Live Transcribe handles the former; doing final GPT-Transcribe work incrementally at VAD boundaries handles the latter. Prove the whole-recording flow first, then compare segmentation against that baseline for speed and accuracy. Waiting only for the last segment is a performance target; backlog and whole-session cleanup also contribute to release-to-insertion latency.
    
5. **Privacy/threat assumptions.** Define what "private" means for this project: no third-party dictation backend, credentials stored locally, audio sent only to the configured model provider, no audio retention by our app by default, no transcript analytics, and contextual information such as repository filenames should only be sent when explicitly enabled. The MVP is private from a third-party dictation company, not fully local/offline. Add privacy and recovery behavior with each capability. Choose memory-only or temporary-disk buffering before capture work, and distinguish API-failure recovery from crash recovery.
    
6. **Important unresolved decisions.** Preserve an explicit open-questions section rather than allowing assumptions to silently harden into architecture. Develop on Windows first; confirm whether macOS is required at launch and record its verification checkpoints. Choose the initial stack, test devices, audio-buffer persistence, and hold-to-talk fallback before implementation. VAD boundaries, maximum segment duration, backlog policy, and measurable acceptance targets remain open. Initial cleanup runs once on the complete canonical transcript, using light cleanup with a bypass; polished cleanup and foreground-app content collection are deferred.
    
7. **Success metrics.** Measure time-to-first-visible-text, release-to-final-insertion latency, canonical accuracy, cleanup meaning changes, lost-dictation rate, and total API cost. Use real probes to set typical and slow-case targets. Before segmentation, save a small evaluation corpus covering short/long speech, corrections, numbers, identifiers, and intended languages.
    
8. **Model assumptions.** Preserve the fact that the specific model names are implementation choices, not product requirements. The semantic roles matter more: `StreamingSTT`, `FinalSTT`, and `CleanupModel`. Keep these roles behind small interfaces from the start and verify account access in the real API probes. Additional provider support remains deferred.
    
9. **A short decision log.** Whenever we make a non-obvious choice later, record something like: `Decision / Alternatives / Why / Revisit when`. Start with Windows-first development, early fixed-text insertion, and single-segment finalization before VAD. Use clipboard + simulated paste initially; if app switching, cursor movement, or a closed target makes the destination uncertain, retain the result and offer Copy. Define recording, finalizing, ready, inserted, failed, and discarded states, including cancellation, late responses, new sessions, and duplicate-insertion prevention.
