## Decisions — 2026-09-21

### D001 — Windows-only initial release

- **Decision:** Build and verify the initial release on Windows. Defer macOS.
- **Alternative:** Require Windows and macOS at launch.
- **Why:** Keep the first release focused and avoid blocking each capability on a second test environment.
- **Revisit when:** macOS work is scheduled and a test device is available. Verify hotkeys, capture, secure storage, insertion, overlay, permissions, and packaging before claiming support.

### D002 — Memory-only audio buffering

- **Decision:** Retain original audio in memory for API retries while the app remains running. Release it after successful finalization or explicit discard. Do not persist recordings to disk; app exit or crash loses pending audio.
- **Alternative:** Temporary-disk buffering with crash recovery.
- **Why:** Keep the first version smaller and avoid recordings left on disk.
- **Revisit when:** Long-session memory use or a need for crash recovery justifies changing the persistence policy.

### D003 — Hold-to-talk preferred

- **Decision:** Prefer hold-to-talk; use toggle-to-record as the initial fallback if the platform probe requires it.
- **Alternative:** Toggle-only interaction from the start.
- **Why:** Preserve the intended hold → speak → release interaction.
- **Revisit when:** The global keybinding probe establishes shortcut or key-up limitations.

## Decisions — 2026-09-22

### D004 — Tauri + TypeScript + Vite initial stack

- **Decision:** Build the Windows-first app with Tauri, TypeScript, and Vite. Keep OS-specific input and insertion behavior behind small platform interfaces for a later macOS port.
- **Alternative:** Electron + TypeScript + Vite, with a native component for global key release if hold-to-talk requires it.
- **Why:** Tauri's global-shortcut plugin exposes pressed and released events, allowing the first Windows keybinding probe without building an Electron-specific native component. The user intends to port to macOS later.
- **Revisit when:** The Windows probe shows unreliable key release or another required desktop capability cannot be implemented acceptably; reassess on a macOS test device before claiming macOS support.

### D005 — Hold-to-talk for the Windows initial interaction

- **Decision:** Start recording on the global shortcut's Pressed event and stop on its Released event. The probe now displays only the hold state; no toggle action is part of the initial interaction.
- **Alternative:** Toggle recording with successive shortcut presses.
- **Why:** After the requested Notepad and VS Code test, the user reported that the shortcut worked and supplied two timestamped key-down/key-up pairs. The prior toggle display was generated by probe code on each press, not by the intended recording lifecycle.
- **Revisit when:** Longer Windows use reveals missed release events or another platform probe requires a fallback.

## Decisions — 2026-09-23

### D006 — WebView microphone capture for the Windows probe

- **Decision:** Capture mono Float32 PCM through the Tauri WebView's microphone API and an AudioWorklet. Keep the PCM in memory, encode a PCM16 WAV in memory for playback, and require an explicit Clear action to discard a stopped recording.
- **Alternative:** Add a native Windows audio-capture dependency and expose the captured buffer through Rust commands.
- **Why:** The probe can exercise device selection, microphone permission errors, capture, and playback without adding a native dependency or writing audio to disk.
- **Revisit when:** Live Windows checks show that WebView permission handling, device disconnect behavior, or capture continuity is unreliable.

### D007 — Prepare microphone access before push-to-talk (superseded by D017)

- **Decision:** Require a one-time **Prepare microphone** action before the recording hotkey is enabled. The action requests permission, refreshes device labels, then stops its temporary stream without retaining audio.
- **Alternative:** Request microphone permission for the first time when the hotkey is pressed.
- **Why:** A permission prompt can consume some or all of a user's hold before capture starts. The first live attempt also returned zero PCM frames, so the updated probe shows AudioContext, AudioWorklet, and track diagnostics when capture is empty.
- **Revisit when:** Manual Windows checks confirm whether preflight resolves the zero-frame result and whether permission remains available after app restart.

## Decisions — 2026-10-01

### D008 — Windows Credential Manager for API-key storage

- **Decision:** Store the user's OpenAI key as a generic Windows credential using `CredWriteW`, `CredReadW`, and `CredDeleteW`, with local-machine persistence for the current Windows user. Keep the target identifier stable: `app.byokdictation.hotkeyprobe/openai-api-key`. The UI receives presence and operation status only; API requests read the key in Rust. Wipe owned Rust secret buffers and the native read allocation before release.
- **Alternative:** Introduce an encrypted app-owned vault or a cross-platform keyring wrapper.
- **Why:** Use the operating system's existing secure storage for the Windows-first probe. The generated Windows API bindings also support native HTTPS validation without adding a separate HTTP client stack.
- **Revisit when:** macOS work begins, a credential migration is needed, or provider configuration expands. Memory wiping is limited to owned buffers and does not guarantee erasure of WebView/IPC/OS copies.

### D009 — Explicit validation independent of saving

- **Decision:** Saving and removing credentials are local operations. Validate only when explicitly requested, using native WinHTTP against OpenAI's models endpoint with certificate checks enabled, no redirects, and 10-second timeouts for each network phase. Surface fixed error codes and discard provider response bodies. Failed validation retains the saved credential.
- **Alternative:** Validate on every launch or require successful network validation before saving.
- **Why:** Secure storage must work offline. A restricted key may lack model-list permissions even when it has permission for another endpoint. Task 5 will verify actual transcription access and request format.
- **Revisit when:** Additional provider settings or a more precise endpoint-specific connection check is introduced.

### D010 — Explicit whole-recording transcription probe

- **Decision:** Task 5 uploads only when the user chooses Transcribe recording. Reuse the existing in-memory WAV encoder, binary Tauri IPC, Windows Credential Manager, and native WinHTTP. Keep final STT behind a small Rust interface with deterministic fakes. Use `gpt-transcribe` with a complete WAV and JSON response, preserving the exact returned canonical text.
- **Alternative:** Upload automatically on hotkey release, add live streaming, or introduce a new HTTP client dependency.
- **Why:** Prove file transcription separately before Task 6 session/insertion integration. Keep credentials in Rust and avoid storing audio on disk.
- **Revisit when:** Task 6 connects final transcription to release-to-insertion behavior, or macOS/provider work changes the native transport.

### D011 — Probe audio release and discard behavior

- **Decision:** Retain PCM/WAV/playback on transcription failure, including malformed or empty successful responses. Release audio once a usable canonical transcript is retained in the view; retain that text until explicit discard or app exit. Discard invalidates late responses. An already-sent native request finishes before another recording is permitted, releasing its owned upload buffers when it returns. Reject empty/invalid WAVs, uploads over 25,000,000 bytes, and successful responses over 1 MiB.
- **Alternative:** Discard audio before a usable transcript exists, silently replace a retained transcript with a new session, or implement native request cancellation now.
- **Why:** Preserve retry and recovery without expanding Task 5 into the full Task 6 lifecycle. Discard cannot retract data already sent to the provider.
- **Revisit when:** Task 6 adds cancellation/new-session rules or long-session buffering requires a different strategy.

### D012 — Single-session dictation and insertion commit boundary

- **Decision:** Task 6 captures a session-bound destination on hotkey press, automatically transcribes the complete recording on release, and inserts the exact canonical result. Allow one session at a time; retained transcripts require explicit discard before another recording. A cancelled sent request keeps its native-work lock until completion. Cancellation is available during capture and transcription; native paste dispatch is a commit boundary after which discard waits for the result.
- **Alternative:** Concurrent sessions, silently replacing retained text, native request cancellation, or automatic repeated paste after an ambiguous outcome.
- **Why:** Preserve dictation and destination ownership while keeping recovery understandable. A session token and native paste latch prevent stale/duplicate insertion. Distinguish paste submission from clipboard restoration; partial or unknown outcomes use Copy rather than automatic retry. A confirmed pre-paste refusal permits original-target hotkey retry without another API request. Microphone interruption retains partial audio for explicit transcription retry.
- **Revisit when:** Daily use demonstrates a need for multiple sessions or native transport cancellation, or a more capable Windows text-destination API can confirm acceptance and track historical focus/caret changes.

## Decisions — 2026-10-02

### D013 — Native cancellable streaming transport and an independent preview

- **Decision:** Task 7 connects directly to `wss://api.openai.com/v1/realtime?intent=transcription` using `gpt-live-transcribe`, a transcription-only session, 24 kHz mono PCM16, `delay: low`, and no server turn detection. Use tokio-tungstenite with native-tls/Windows certificate validation. Keep credential retrieval and Authorization in Rust; the UI receives sanitized status and transcript events through a session-bound Tauri channel. Retain the existing WinHTTP transport for final file transcription.
- **Alternative:** Add concurrent WinHTTP WebSocket send/receive workers or expose temporary authentication to a browser connection.
- **Why:** Async connect/send/receive futures can be dropped on cancellation without unsafe shared-handle lifetime management or returning authentication to the WebView. A small StreamingSTT seam and in-memory WebSocket peers support deterministic protocol tests. The current official transcription guide and a real saved-key configuration probe established model/configuration access.
- **Revisit when:** Proxy support, another provider/platform, or measured performance justifies a transport change. Explicitly owned temporary secret strings are wiped; third-party handshake/header/TLS allocations are not guaranteed to be wiped.

### D014 — Bounded live preview with explicit reconnect

- **Decision:** Store original microphone PCM first, then independently convert a preview copy. Limit frontend queued PCM to 192,000 bytes plus one in-flight chunk, native queue capacity to 32 chunks of at most 9,600 bytes, and individual provider messages/live preview to 1 MiB (UTF-16 storage budget for preview text). Stop the preview on backlog or connection failure while recording continues. Reconnect explicitly from current audio, retain earlier provisional words, mark the gap, and ignore old connection events. Commit one live audio turn on release; local VAD remains Task 14.
- **Alternative:** Unbounded buffering, automatic reconnect/replay of previous audio, or treating live text as the insertion result.
- **Why:** A preview failure must not affect canonical transcription or grow memory indefinitely. Whole-recording final STT remains authoritative. Replaying partial live turns would require additional transcript reconciliation and recovery semantics.
- **Revisit when:** The evaluation baseline establishes a need for automatic reconnect or different queue/latency limits. The probe's area-averaging resampler is independent of original audio and may need a higher-quality filter after representative microphone testing.
- **Probe UX:** A new hotkey action retains audio on release and skips destination capture/automatic insertion, allowing safe live-text/playback/retry checks. Normal dictate mode also supports the optional live preview and preserves its existing release-to-canonical-insertion flow. Discard clears both transcripts and cancels the live connection.

## Decisions — 2026-10-03

### D015 — Passive status overlay with main-window recovery

- **Decision:** Task 8 adds a separate hidden-on-start, always-on-top, nonfocusable, mouse-through status WebView. Capture the original destination before showing it. Use native Windows `ShowWindow(SW_SHOWNOACTIVATE)` for every show and the matching native hide path; position within the foreground monitor's work area. Render fixed placeholder/status copy first; live text remains Task 9. Keep Retry/Copy/Restore/Discard in the tray-accessible main probe.
- **Alternative:** Show an activating or interactive window during dictation, reuse the main frontend in a second WebView, or connect live deltas before proving the window lifecycle.
- **Why:** Preserve destination focus and session ownership. The overlay receives only an ownership generation, revision, and fixed phase; it cannot invoke credential, capture, transcription, paste, or overlay-write commands. Serial/coalesced updates protect discard; a native generation rejects queued updates from a previous frontend after development reload. Errors and clipboard-recovery warnings persist; successful insertion or explicit discard hides the panel without discarding retained text.
- **Reference:** [Microsoft ShowWindow documentation](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-showwindow) defines the nonactivating show behavior; native styles and foreground focus were also verified on this Windows machine.
- **Revisit when:** Task 9 needs bounded provisional text display, or user testing justifies interactive overlay recovery, placement settings, or a broader mixed-DPI/platform matrix.

### D016 — Bounded provisional text in a passive overlay

- **Decision:** Task 9 publishes only the current session's enabled provisional preview, retaining the latest 2,048 UTF-16 units in the overlay. Include fixed preview status and reconnect-gap feedback, compare full content for updates, render plain text, and keep the complete existing live view in the main probe. Preserve destination-before-show, native nonactivation, read-only overlay access, owner/revision guards, and main-window recovery.
- **Alternative:** Send the complete 1 MiB live preview on every update, insert provisional text directly, or add interactive overlay controls now.
- **Why:** Words must update while the phase stays Listening, without unbounded IPC/window content or losing destination focus. Preview errors remain independent of local recording/canonical finalization. Hide clears both native state and the overlay DOM; live words never become insertion input.
- **Revisit when:** Task 10's combined-flow testing or representative long-session/DPI evaluation demonstrates a need for another display budget, placement, or interaction.

### D018 — Actionable recovery and confirmed manual copy during stalled processing

- **Decision:** Show the specific issue and available actions in Dictation for failed, stalled, and clipboard-restoration states. Keep recovery visible during finalization. Already sent requests can finish in the background; native busy refuses a newer request promptly and retains its new audio for retry.
